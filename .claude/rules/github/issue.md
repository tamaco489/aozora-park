# Issue のルール

## 2 つの進め方

作業は 2 通りのどちらかで進める。**どちらにするかは開発者が決める。** 迷ったら聞く。

| 進め方           | 使う場面                                      | ブランチ                                        | Issue                     |
| ---------------- | --------------------------------------------- | ----------------------------------------------- | ------------------------- |
| リリースブランチ | 複数の PR にまたがるまとまり (マイルストーン) | `main` → `release/...` → `feature/...`          | メイン 1 本 + サブ 複数本 |
| 直接             | 軽微な修正、抜け漏れの対応                    | `main` → `hotfix/...` / `chore/...` などの 1 本 | 単体 Issue 1 本           |

## ブランチ名

**Issue 番号を含める。**

```text
<種別>/<main-issue|sub-issue|issue>-<Issue 番号>/<内容>
```

| ブランチ                        | 切る元                   | 番号の由来          |
| ------------------------------- | ------------------------ | ------------------- |
| `release/main-issue-12/setup`   | `main`                   | メイン Issue の番号 |
| `feature/sub-issue-13/buf-init` | 対応するリリースブランチ | サブ Issue の番号   |
| `chore/issue-20/fix-lint`       | `main`                   | 単体 Issue の番号   |

- 種別は `commit-types.md` の type と同じものを使う (`feature` だけは `feat` ではなくこの綴り)
- サブ Issue と単体 Issue の種別は、タイトルの変更種別に合わせる (`[ci] [ci] ...` なら `ci/sub-issue-<番号>/...`)
- 単体 Issue は親子関係を持たないため `issue-<番号>` とする
- `<内容>` は英小文字とハイフンで短く付ける
- サブ Issue の PR は base をリリースブランチにする

リリースブランチはすべてのサブ Issue が閉じたら `main` へマージし、メイン Issue を閉じる。

## テンプレート

**本文の型は `.github/ISSUE_TEMPLATE/` が唯一の正とする。** Issue を作るときは対応するファイルを読んで、その見出し構成のまま埋める。

| テンプレート | 用途                                 |
| ------------ | ------------------------------------ |
| `main.md`    | メイン Issue (リリース単位)          |
| `sub.md`     | サブ Issue (PR 1 本ぶん)             |
| `single.md`  | 単体 Issue (main から直接進める作業) |

- 埋められない項目 (「補足」「背景・目的」など) は残さず削除する
- コメント (`<!-- -->`) は残さない
- メイン Issue とサブ Issue をまとめて作るときは `create-release-issues` スキルを使う。単体 Issue はスキルを使わず、`single.md` に従って作る

## タイトル

```text
メイン: [milestone-<番号>] <マイルストーン名>
サブ:   [ラベル] [変更種別] <タイトル>
単体:   [ラベル] [変更種別] <タイトル>
```

- ラベルは `labels.md` から選ぶ。変更種別は `commit-types.md` の type と同じ
- メイン Issue は複数のスコープにまたがるためラベルを付けない
- マイルストーン以外のまとまりでは `[milestone-<番号>]` の代わりに `[release] <名前>` を使う

**PR のタイトルは Issue の種類ごとに決まる** (`pr-description.md`)。

| Issue  | Issue のタイトル                | 対応する PR のタイトル                   |
| ------ | ------------------------------- | ---------------------------------------- |
| メイン | `[milestone-0] 準備`            | `[Release] [milestone-0] 準備`           |
| サブ   | `[backend] [feat] buf を初期化` | `[sub] [milestone-0] buf を初期化`       |
| 単体   | `[docs] [docs] README を更新`   | `[docs] [issue-20] [docs] README を更新` |

## 親子の紐付け

GitHub のサブ Issue 機能で紐付ける。本文にチェックリストで一覧を書かない。

- 作成時に紐付ける場合は `issue_write` の `parent_issue_number` を使う
- あとから紐付ける場合は `sub_issue_write` を使う (`sub_issue_id` は Issue 番号ではなく ID)

## Issue を閉じる

**サブ Issue は PR がマージされても自動では閉じない。** GitHub が `Closes #N` で自動的に閉じるのは
base が既定ブランチ (`main`) の PR だけで、サブ PR の base はリリースブランチのため対象外になる。

- サブ PR をマージしたら、対応するサブ Issue を手で閉じる。完了条件の確認結果をコメントに残す
- メイン Issue はリリースブランチを `main` へマージした時点で `Closes #N` により自動で閉じる
- 単体 Issue も base が `main` のため自動で閉じる

## 書くこと・書かないこと

- **完了条件は動作で確かめられる形にする** (「buf generate が通り、Go と TS のコードが生成される」)
- 実装方法をコードで書かない。決めるべきことと、決めた理由を書く
- 設計の詳細はドキュメントへのリンクで済ませる

## ラベル

GitHub 上のラベルは未整備で、`labels.md` のラベルは登録されていない。
**存在しないラベルを Issue に付けようとするとエラーになるため、当面は GitHub のラベルを付けない。**
分類はタイトルの接頭辞で行う。
