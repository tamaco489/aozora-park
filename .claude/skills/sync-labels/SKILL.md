# Sync Labels — GitHub ラベル同期スキル

`.claude/rules/github/labels.md` を正として、GitHub 上のラベルをその状態に合わせる。

**定義ファイルを書き換えない。** 一方向 (定義 → GitHub) にだけ反映する。

## 処理ステップ概要

| Step | 内容               | 概要                                                     |
| ---- | ------------------ | -------------------------------------------------------- |
| 1    | 前提の確認         | `gh` が使えること、対象リポジトリを確定する              |
| 2    | 定義の読み込み     | `labels.md` の表から名前・色・説明を取り出す             |
| 3    | 現状の取得         | GitHub のラベルと、付いている Issue・PR を取得する       |
| 4    | 差分の算出         | 改名・更新・追加・削除の 4 つに分ける                    |
| 5    | 警告とバックアップ | 削除の影響を警告し、控えを取るかを聞く                   |
| 6    | 計画の提示         | 差分を一覧にして承認を得る。削除は 1 件ずつ確認する      |
| 7    | 適用               | 改名 → 更新 → 追加 → 削除 の順に 1 件ずつ実行する        |
| 8    | 検証と結果報告     | 取得し直して一致を確かめ、実行内容と控えの場所を報告する |
| 9    | 振り返り           | 今回の進め方を振り返り、改善案があれば提案して反映する   |

## 制約事項

- **削除は取り消せない。** 付いていた Issue と PR からラベルが外れ、履歴も残らない。**1 件ずつ承認を得る**
- **改名は安全。** GitHub はラベルを ID で持つため、付いている Issue と PR はそのまま追随する
- `gh label create --force` を使わない。既存かどうかを自分で判断し `create` と `edit` を使い分ける
- 適用は 1 件ずつ順番に実行する (並列実行禁止)
- 定義ファイルは読むだけで書き換えない

## 各ステップの詳細

### Step 1: 前提の確認

```bash
gh auth status
gh repo view --json nameWithOwner -q .nameWithOwner
```

- `gh` が未認証なら、**ユーザーに認証を依頼して中断する**
- 対象リポジトリを表示し、これでよいか確認する

### Step 2: 定義の読み込み

`.claude/rules/github/labels.md` の表を読む。

- 表の列は「ラベル」「色」「対象スコープ」。バッククォートを外して値を取る
- **ファイルが無い場合は、定義の場所をユーザーに聞く。** 推測で別のファイルを読まない
- 色は `#` を外した 6 桁の 16 進にする
- 説明は「対象スコープ」の文言を使う。**GitHub の説明は 100 文字までのため、超える場合は括弧の中を削る**

読み取った内容を一覧で示し、意図どおりかを確認する。

### Step 3: 現状の取得

```bash
gh label list --limit 100 --json name,color,description
gh issue list --state all --limit 200 --json number,title,labels
gh pr list --state all --limit 200 --json number,title,labels
```

Issue と PR も取るのは、削除の影響が何件に及ぶかを Step 5 で示すため。

### Step 4: 差分の算出

| 区分 | 条件                                      | 操作                   |
| ---- | ----------------------------------------- | ---------------------- |
| 改名 | 定義外のラベルに Issue か PR が付いている | `gh label edit --name` |
| 更新 | 名前が一致し、色か説明が違う              | `gh label edit`        |
| 追加 | 定義にあり GitHub に無い                  | `gh label create`      |
| 削除 | 定義外で、どこにも付いていない            | `gh label delete`      |

**定義外のラベルがどこかに付いている場合は、まず改名を検討する。** 削除して作り直すと履歴が失われるため。

改名先は意味で決まるので機械的には判定できない (`infrastructure` → `infra` など)。**候補を添えて提示し、改名するか削除するかをユーザーに決めてもらう。**

改名しても、そのラベルが付いている Issue と PR の分類が新しい語彙で正しいとは限らない。**ずれているものは報告に含める。** 付け替えはこのスキルでは行わない。

### Step 5: 警告とバックアップ

**削除が 1 件も無い場合、この Step を飛ばす。** 改名・更新・追加だけなら既存の Issue と PR からラベルは外れない。

削除がある場合、適用の前に影響を必ず警告する。

```text
以下のラベルは削除されます。付いている Issue と PR から外れ、元に戻せません。

  docs   Issue 2 件、PR 3 件に付いています
```

そのうえで、**番号で選ばせる。** 選択肢の文言を打たせない。

```text
バックアップを取りますか。番号で答えてください。

  1: バックアップを取ってから更新する (既定)
  2: バックアップは取らずにそのまま更新する
```

| 入力       | 動作                                        |
| ---------- | ------------------------------------------- |
| `1` か空欄 | `tmp/` に控えを書き出してから Step 6 へ進む |
| `2`        | そのまま Step 6 へ進む                      |

想定外の入力なら、もう一度同じ選択肢を出す。**勝手に既定で進めない。**

控えの書き出し方。

- `templates/backup.md` の雛形を使い、`tmp/labels-backup-<YYYYMMDD-HHMMSS>.md` に書き出す
- `tmp/` が無ければ作る。`tmp/` は `.gitignore` の対象
- 書き出したパスを Step 8 で報告する

### Step 6: 計画の提示

```text
以下の内容で GitHub のラベルを更新します。よろしいですか？

[改名] infrastructure → infra  (色 5319e7 → b22ac3)
[更新] backend   色 1d76db → 4147d4
[追加] proto     色 00b8d9  Protocol Buffers と buf の設定
[削除] old-label  どこにも付いていません
```

**削除は他の操作と一緒に承認させない。** 1 件ずつ、付いている件数を添えて確認する。

### Step 7: 適用

改名 → 更新 → 追加 → 削除 の順に実行する。改名を先にするのは、定義側の名前で新規作成してしまい重複するのを避けるため。

```bash
gh label edit <旧名> --name <新名> --color <色> --description "<説明>"
gh label edit <名前> --color <色> --description "<説明>"
gh label create <名前> --color <色> --description "<説明>"
gh label delete <名前> --yes
```

- 1 件失敗したらそこで止め、どこまで適用できたかを報告する
- 権限不足で失敗した場合は、**ユーザーに実行を依頼する**

### Step 8: 検証と結果報告

`gh label list` を取り直し、定義と突き合わせる。

- 名前・色・説明の 3 つが一致することを確認する
- 一致しないものがあれば、その内容をそのまま報告する。**成功したと報告しない**

報告する内容。

- 改名・更新・追加・削除の件数と内訳
- 控えを書き出した場合はそのパス
- 新しい語彙とずれたまま残っている Issue と PR のラベル
- 失敗した操作があればその内容と原因

### Step 9: 振り返り

**このスキルを実行した過程を振り返り、次に同じ作業をするときに効率が上がる点があれば提案する。**

振り返る観点。

| 観点           | 見るところ                                                                   |
| -------------- | ---------------------------------------------------------------------------- |
| 手戻り         | ユーザーの指摘で計画を作り直した箇所。判断の基準が規約に無かったのではないか |
| 確認の往復     | 何度も聞き返した点。既定値を決めれば聞かずに済むのではないか                 |
| 判断に迷った点 | 改名か削除かのように、機械的に決められなかった箇所                           |
| 定義とのずれ   | `labels.md` の書き方が読み取りにくかった箇所                                 |
| 手順の抜け     | このスキルに書かれていないのに必要になった作業                               |
| 分類のずれ     | 同期後に、新しい語彙と合わないまま残った Issue と PR のラベル                |

進め方。

- **改善案が無ければ「なし」と伝えて終わる。** 無理に作らない
- 提案は多くても 3 件。「観察した事実 → 何が困るか → どのファイルをどう直すか」の形で書く
- **ユーザーが採用したものだけ修正する。** 修正前に diff を提示して承認を得る (`.claude/rules/general/workflow.md`)
- 修正対象は `SKILL.md`、`templates/`、`.claude/rules/github/labels.md` に限る。GitHub 上のラベルは修正対象にしない
- 修正してもコミットはしない (`smart-commit` に任せる)
