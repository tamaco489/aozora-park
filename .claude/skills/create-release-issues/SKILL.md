# Create Release Issues — メイン Issue・サブ Issue 作成スキル

マイルストーン 1 つを、メイン Issue 1 本とサブ Issue 複数本に分けて作成する。

**単体 Issue はこのスキルの対象外。** `.claude/rules/github/issue.md` に従い `single.md` で作る。

## 処理ステップ概要

| Step | 内容              | 概要                                                      |
| ---- | ----------------- | --------------------------------------------------------- |
| 1    | 規約の読み込み    | ルールとテンプレートを読む                                |
| 2    | 対象の把握        | どのマイルストーンを Issue 化するかを確定する             |
| 3    | 進め方の確認      | リリースブランチ方式でよいかを確認する                    |
| 4    | サブ Issue の分割 | 分割案を提示し、ユーザーと対話して確定する                |
| 5    | 内容の確定        | 各 Issue のタイトルと本文を作り、一覧で提示して承認を得る |
| 6    | メイン Issue 作成 | GitHub MCP で作成する                                     |
| 7    | サブ Issue 作成   | 親に紐付けながら 1 件ずつ作成する                         |
| 8    | 結果報告          | 作成した Issue の番号・タイトル・URL を報告する           |
| 9    | 振り返り          | 今回の進め方を振り返り、改善案があれば提案して反映する    |

## 制約事項

- **Issue の作成は Step 5 の承認を得てから行う**
- **サブ Issue は 1 件ずつ順番に作成する** (並列実行禁止)
- 本文の型は `.github/ISSUE_TEMPLATE/` を正とし、このファイルにテンプレートを持たない
- **サブ Issue には GitHub のラベルを付ける。** 触る予定の領域すべてを選ぶ。複数で構わない (`.claude/rules/github/labels.md`)
- **メイン Issue にはラベルを付けない。** 影響範囲はサブ Issue が揃うまで確定しないため、リリース PR を出す段階で付け直す
- Issue の作成には GitHub MCP (`issue_write`) を使う。`gh issue create` は使わない

## 各ステップの詳細

### Step 1: 規約の読み込み

以下を読む。

- `.claude/rules/github/issue.md` — 進め方、タイトル、親子の紐付け
- `.claude/rules/github/labels.md` — ラベルの選択
- `.claude/rules/github/commit-types.md` — 変更種別
- `.github/ISSUE_TEMPLATE/main.md` — メイン Issue の本文
- `.github/ISSUE_TEMPLATE/sub.md` — サブ Issue の本文

### Step 2: 対象の把握

Issue 化する対象を確定する。ユーザーが指定しない場合は聞く。

- Notion の URL を渡された場合は Notion MCP (`notion-fetch`) で読む
- マイルストーン番号だけを渡された場合は、設計ドキュメントの該当箇所を読む
- 「マイルストーン名」「主な作業」「完了条件」の 3 点が揃うまで進まない

**設計だけでなく実装の現状も確認する。** 設計ドキュメントは「こうする」を書いたもので、どこまで出来ているかは書かれていない。

- 対象が触るディレクトリのファイルを実際に読む (`proto/` `backend/` `frontend/` `infra/`)
- 依存の追加が要るかを `go.mod` と `package.json` で確かめる
- **設計と実装が食い違っている箇所を控える。** 分割の単位か、サブ Issue の補足に反映する

### Step 3: 進め方の確認

`.claude/rules/github/issue.md` の 2 つの進め方のうち、リリースブランチ方式でよいかを確認する。

- 複数の PR に分かれない軽微な作業だと判断できる場合は、**このスキルではなく単体 Issue で足りることを伝えて中断する**
- リリースブランチの `<名前>` の部分をユーザーと決める (`setup` のような短い英小文字)
- 番号はメイン Issue の作成後に確定するため、この時点では `release/main-issue-<番号>/<名前>` の形で保留する

### Step 4: サブ Issue の分割

**分割案を作る前に、規約に埋まっている保留を拾う。** `.claude/rules/` の `> [!NOTE]` を検索し、このマイルストーンが発火条件になっているものを洗い出す。

- 「最初の業務機能を作る時点で」「実装が始まってから」のように、時期が書かれたものを探す
- 該当するものは、サブ Issue の「やること」に入れるか、独立したサブ Issue にする
- **NOTE を書き換えるところまでを完了条件に含める。** 保留のまま残すと次のマイルストーンでも同じ見落としが起きる

**ユーザーと対話して分割を決める。** スキルが独断で確定しない。

分割案を作る際の基準。

| 基準                  | 内容                                                       |
| --------------------- | ---------------------------------------------------------- |
| PR 1 本に収まる大きさ | レビューできる粒度。1 サブ Issue = 1 PR                    |
| 同じ関心でまとまる    | proto の定義と Go の実装のように、目的が同じものはまとめる |
| 依存の順に並べる      | 先に必要なものを前に置き、依存があれば明示する             |
| 担当範囲が重ならない  | 同じファイルを 2 つのサブ Issue が触らない                 |

分割案は次の形で提示し、追加・統合・分割・順序変更の要望を受けて確定する。

```text
以下の分割でサブ Issue を作成します。よろしいですか？

[サブ 1] [sub] [chore] モノレポの雛形を作成
  - ディレクトリ構成、go.mod、.gitignore

[サブ 2] [sub] [feat] buf の初期化と hello world proto の追加
  - buf.yaml / buf.gen.yaml、proto の定義、生成コードのコミット

[サブ 3] [sub] [chore] docker compose に Firestore エミュレータを追加
```

### Step 5: 内容の確定

テンプレートに沿って各 Issue のタイトルと本文を作り、**すべてまとめて提示して承認を得る。**

- タイトルは `.claude/rules/github/issue.md` の形式に従う
- 埋められない項目とコメント (`<!-- -->`) は削除する
- メイン Issue の「完了条件」はマイルストーンの完了条件を使う
- サブ Issue の「完了条件」は、そのサブ Issue 単体で確かめられる形にする
- サブ Issue の「作業ブランチ」の base は Step 3 で決めたリリースブランチにする。番号が未確定の部分は Step 6・7 で埋める

### Step 6: メイン Issue 作成

```text
issue_write(method: "create", owner, repo, title, body)
```

作成された Issue 番号を控える。**ラベルは付けない。** 影響範囲が確定する `create-release-pr` の段階で付ける。

### Step 7: サブ Issue 作成

Step 4 で決めた順に 1 件ずつ作成する。`parent_issue_number` にメイン Issue の番号を渡し、作成と紐付けを同時に行う。

```text
issue_write(method: "create", owner, repo, title, body, labels: ["<ラベル>"], parent_issue_number: <メイン Issue の番号>)
```

`labels` には、そのサブ Issue で触る領域すべてを渡す (`[sub] [feat] buf の初期化` なら `proto` `backend` `frontend`)。
**タイトルに領域は書かないため、ラベルだけが領域を表す。**
**GitHub 上に無いラベルを渡すとエラーになる。** その場合は `sync-labels` スキルで同期してから作り直す。

作成のたびに返ってきた Issue 番号で、本文の「作業ブランチ」を確定させる。

```text
issue_write(method: "update", owner, repo, issue_number, body: <番号を埋めた本文>)
```

- 1 件失敗したらそこで止め、どこまで作成できたかを報告する
- 作成済みの Issue を消さない (ユーザーが判断する)

### Step 8: 結果報告

以下を報告する。

- メイン Issue の番号・タイトル・URL
- サブ Issue の番号・タイトル・URL の一覧 (作成順)
- リリースブランチ名と、次にやること (ブランチを切って最初のサブ Issue に着手する)
- エラーが発生した場合はその内容と、どこまで作成できたか

### Step 9: 振り返り

**このスキルを実行した過程を振り返り、次に同じ作業をするときに効率が上がる点があれば提案する。**

振り返る観点。

| 観点                 | 見るところ                                                       |
| -------------------- | ---------------------------------------------------------------- |
| 手戻り               | ユーザーの指摘で作り直した箇所。指示が規約に無かったのではないか |
| 確認の往復           | 何度も聞き返した点。既定値を規約に書けば聞かずに済むのではないか |
| 判断に迷った点       | 規約が曖昧、または規約同士が食い違っていた箇所                   |
| テンプレートの過不足 | 毎回削除する項目、毎回書き足す項目                               |
| 手順の抜け           | このスキルに書かれていないのに毎回必要になった作業               |

進め方。

- **改善案が無ければ「なし」と伝えて終わる。** 無理に作らない
- 提案は多くても 3 件。「観察した事実 → 何が困るか → どのファイルをどう直すか」の形で書く
- **ユーザーが採用したものだけ修正する。** 修正前に diff を提示して承認を得る (`.claude/rules/general/workflow.md`)
- 修正対象は `SKILL.md`、`.claude/rules/`、`.github/ISSUE_TEMPLATE/`、`.github/PULL_REQUEST_TEMPLATE/` に限る。Issue の内容は修正対象にしない
- 修正してもコミットはしない (`smart-commit` に任せる)
